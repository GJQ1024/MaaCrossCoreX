# 竞技场（模拟军演）实机验证记录

> 设备：MuMu <实例>（adb 127.0.0.1:<port>），横屏 1280×720。
> 本文只记录实测结论，不含账号信息。

## 1. 坐标基准（本轮最大坑）

- `wm size`：`Physical size: 720x1280`，**无 Override**；`mRotation=ROTATION_90`，bounds `Rect(0,0-1280,720)`；`screencap` 输出 **1280×720**。
- 结论：`adb shell input tap` 直接使用 **1280×720 逻辑坐标**，不需要旋转/竖屏映射。
  - 验证：点 (838,645)（挑战按钮中心）命中并成功进入战斗；按竖屏旋转映射算出的 (616,452) 无效。
- 踩坑：审图时工具把截图缩放到 **1024×576** 显示，误把显示坐标当 1280 坐标使用会造成约 0.8 倍偏移。
  读图坐标必须先 ×1.25 再点。历史上记录的 (839,517) 即因此错位（按钮实际在 y≈622 起）。

## 2. 进入竞技场

### 自动战斗状态不继承（权威结论）

**自动战斗是用户可改、且会被上一次手动操作改变的 UI 状态，必须主动纠正，不得假定继承。**

- 2026-11-03 定稿：`竞技场_确认自动战斗` 是三段式「确保开态」闸，不是「验证已开」：
  ①已开 → **颜色 + 形状双重判据**连续 2 帧达标（ROI `[1096,34,78,46]`）直接通过、不点击；
  ②关态 → AutoOff 模板连续 2 帧命中（阈值 0.9）→ 点击图标 → 0.9s → 连续 2 帧复核，
  仍关再点一次（最多 2 次）；③识别不到（演出中/HUD 未出）→ **不判失败**，预算 65s 内继续等待，
  HUD 出现即回到①②。仅预算耗尽仍既判不到开态、也点不到按钮才失败。

#### 双重判据（2026-11-03 升级，2026-11-03 离线实测取值）

单靠「琥珀像素计数」挡不住**落在计数区间内的大面积金色**：实测金色战斗横幅
（`poll_093.png` / `poll_100–119.png`）为 **774** 像素，落在 120–1000 区间内会被误判为开态。
因此在计数之上再加一层形状校验，取最大连通块 + 主体块联合外框：

| 维度 | 判据 | 实测来源（1280×720，ROI 78×46） |
| --- | --- | --- |
| 颜色 | 琥珀 R 160–255 / G 110–230 / B 30–180，R-B≥45、G-B≥20（RGB/BGR 双分支） | 开态帧 161–196 |
| 计数 | ROI 琥珀像素 120–1000 | 正例 161–196；关态 0；主界面 65；整片金 3588 |
| 最大块面积 | 60–130 px | 正例 79–85；金色横幅 528；整片金 3588；主界面噪点 28；列表碎点 4 |
| 主体框宽 | 17–28 px | 正例 20–24 |
| 主体框高 | 18–27 px | 正例 22–23 |
| 宽高比 | 0.77–1.26 | 正例 0.909–1.091（各留 15%） |
| 填充率 | 0.26–0.42 | 正例 0.305–0.366（环形图标非实心） |

- 「主体块」= 面积 ≥ 最大块 50% 的连通块。开态图标是**两枚等大的环状箭头**（81/80、85/83、85/82），
  单块外框会随哪半箭头更大而左右翻转，正例单块宽高比实测 **0.500–2.111**，与负例
  `poll_093.png` 的 0.632 **直接重叠**——所以不能用单块外框，改用两枚箭头的外接并集框。
- 各阈值均按正例实测值上下留 ≥15% 余量，无 0.002 式贴边；运行时按 ROI 实际分辨率缩放
  （1920×1080 放大帧复核：面积 170、框 35×32、宽高比 1.094、填充率 0.303，仍判开态）。
- `poll_088.png`（整片金色，3588）被**面积上限 130**、宽 78、高 46、宽高比 1.696、填充率 1.0 挡掉；
  `poll_093.png`（金色横幅，774）被**面积上限 130**（528）挡掉，同时高 38、宽高比 0.632、填充率 0.579
  也全部越界。二者计数都在区间内，是形状判据真正生效的样本。
- 实现选 **agent 侧 CustomRecognition**（`agent/combat_autobattle.py`），不用原生 `ColorMatch`：
  原生只能给「颜色区间 + 像素总数 + 联合外框」，没有最大连通块面积/填充率/连通块数的图元，
  无法在 pipeline 里表达这些约束。无框时返回 `None`，绝不返回 `(0,0,0,0)`（P-004）。
- 旧 `AutoOn.png` 0.802 vs 阈值 0.8 的 0.002 贴边判据已废弃；`AutoOff.png` 实测 0.962 vs 0.9，余量 0.062。
- 节点 `竞技场_确认自动战斗` `timeout` 70s（必须大于识别预算 65s）；`[JumpBack]跳过首领演出动画`
  与 `[JumpBack]跳过首领演出动画_OCR` 保留在 `竞技场_等待结算` 的 `next` 首位，不因用户关闭演出而删除。
- 通用原则（其他「会粘住上次设置」的开关同理）见 `docs/项目规范.md` §12。

### 超回合卡死与 60s 看门狗（权威结论）

**游戏侧 bug：竞技场超过回合上限会一直卡住不出结算。** 自动化必须自带看门狗兜底：

- 计时器在 agent 侧（`agent/arena_pipeline.py`），从**战斗 HUD 首次出现**（`combat_autobattle.HUD_FIRST_SEEN`）
  起算 **60 秒**；60s 仍未进结算 → 主动撤退 → 回对手列表 → **刷新对手** → 重新挑战。
- 单轮最多主动撤退 **2 次**；超过则按 `finish` 收尾、回主界面并上报「连续超回合」，
  避免「打不动 → 撤退 → 刷新 → 再打」死循环。
- HUD 迟迟不出现时，按「挑战点击后 75s 宽限 + 60s」兜底起算，并有 180s 硬上限。
- 撤退**不判负、不扣模拟次数**（实测 `3/10 → 3/10`）；刷新为每日 **15 次免费**次数
  （实测 `15/15`），不是无限次、也不是付费刷新。撤退后刷新复用既有 `ArenaRefresh` 节点 /
  `arena_refresh.png`，与 `竞技场_刷新归零` 同一套，不另造逻辑。

### 撤退链走完仍退不出去 → 重启游戏（最后一层兜底）

60s 超时后**先走上面的撤退链**；只有撤退链走完仍退不出去，才允许重启游戏进程：

- 触发条件（任一）：两次点暂停都不出暂停菜单；退出确认弹窗识别不到（禁止盲点确定）；
  确认退出后 **40s** 仍未回到对手列表。
- 手段：`am force-stop` + `monkey`（与 P-010 同手段，`agent/arena_pipeline.py::_restart_game`），
  包名用 `pm list packages` 按 `crosscore` 关键字识别，**认包不认端口**；0 个或多命中都拒绝重启。
- 频次：整个竞技场任务每轮最多重启 **1 次**（`MAX_GAME_RESTARTS_PER_ROUND`），防止「重启→再卡→再重启」。
- 出口：agent 置 `decision=stop_battle_restart` → Pipeline `竞技场_决策撤退失败重启`（finish）→
  `通用_回主界面并结束`。重启后停在标题页，收尾链的 JumpBack 含「开始游戏」可回到主界面。
  **该收尾落点未经实机验证**（节点 `next_doc` 已标 `TODO(pipeline 落点待实机)`），首次触发后需补证据。
- 未撤退完就重启仍属违规：画面仍在变、暂停/退出还能走时，不允许重启。

### 与 P-010「画面停摆 → 重启」兜底的边界

两者都是「无响应兜底」，但**判据不同，手段不再互换**；重启只是最后一层兜底：

| | P-010 停摆（教程/战斗冻结） | P-018 竞技场超回合（本节） |
| --- | --- | --- |
| 判据 | **画面完全不变**：连抓 5 帧，唯一 hash < 2 | **画面仍在变**：HUD/回合推进正常，但 60s 不出结算 |
| 识别手段 | 帧 hash 去重计数 | agent 侧墙钟（HUD 首现 +60s） |
| 处置 | `am force-stop` + `monkey` 重启进程并回大厅 | 先撤退/刷新/重挑；**撤退链走完仍退不出去才** `am force-stop` + `monkey` 重启 |
| 适用边界 | 输入/动画全冻结、点击无响应 | 可点击、可撤退，仅结算卡死；撤退失效才落到重启 |
| 误用后果 | 用撤退处理冻结：点击也无效，白等 | 撤退链没走完就重启：白丢登录态与进度 |

该分类原则同步写入 `docs/项目规范.md` §13。
