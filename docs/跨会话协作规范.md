> 权威级别：权威结论

# 跨会话协作规范

> 适用对象：所有在本仓库（`MCC_Framework`，分支 `feat/relative-coords`）上工作的会话，
> 包括主会话、并行会话和接手会话。本文解决两个问题：**信息孤岛**（问题只留在某个会话里）
> 和**汇报不统一**（用户无法判断进度与是否卡住）。
> 配套台账见 [`docs/问题登记.md`](问题登记.md)；设备条款见 [`docs/device.md`](device.md)。

---

## 1. 长任务必须切段

- 长任务必须切成**有明确终点的段**，每段开始前说清"这一段要交付什么"。
- **每段结束即回报**，不允许一段里闷头跑到底。
- 段的终点必须是可观测的产物或状态，例如：文件写入 + 校验 PASS、某条命令有明确结果、某个节点实机跑通。
- 尚未到达段终点就继续执行，不得用"仍在进行"作为段内沉默的理由。

## 2. 单步超过约 3 分钟无结果 → 停手回报

- 单步（一次命令、一次任务、一次实机操作）超过约 **3 分钟**没有可判断的结果，立即停手。
- 停手回报必须回答三件事：**卡在哪**（当前步骤与目标）、**试了什么**（已执行的命令/操作与结果）、**在等什么**（缺环境、缺权限、缺用户输入，还是等外部进程）。
- 不允许用重复执行、加长超时、反复等待来"熬过"卡住步骤。

## 3. 同类操作连试 2 次无效 → 停手

- 同一类操作（同一命令、同一参数、同一套点击路径）连试 **2 次**仍无效，必须停手。
- 第 3 次尝试前必须先说明"这次改了什么变量、为什么认为会不同"，并登记到 `问题登记.md`。
- 不得以"再试一次看看"为由硬试超过 2 次。

## 4. 每次回报的固定状态头

每次回报（无论长短、无论是否完成）第一行固定写成：

```
进度: 第 n 步 / 共 m 步 | 用户已直接沟通: 是/否 | 状态: 进行中/卡住/完成
```

- `n / m`：当前在本次任务的第几步、共几步；任务不确定总步数时，`m` 写当前已知计划步数，并在正文说明"计划待细化"。
- `用户已直接沟通`：本会话是否直接收到过用户的原始指令/反馈。只有上游会话转述、没有用户原话时为 `否`。
- `状态`：只允许 `进行中 / 卡住 / 完成`。`卡住` 必须在正文写清第 2 节的三件事。

示例：

```
进度: 第 3 步 / 共 6 步 | 用户已直接沟通: 否 | 状态: 卡住
卡在哪：实机任务启动后 90s 未进主界面。
试了什么：重连 ADB 一次（成功）、重跑任务一次（同样卡住）。
在等什么：需要确认模拟器是否被其他会话占用。
```

## 5. 指令标记约定

- 下发指令时，下发方必须在指令开头标注二选一：
  - `[用户未直接沟通]`：指令来自上游转述/二手整理，未与用户当面确认。
  - `[用户已直接沟通]`：指令来自用户原话或用户当面确认。
- 标 `[用户已直接沟通]` 时，**用户当面说法优先于指令文字**；两者冲突时以用户为准，
  并在回报中写明分歧点（"指令写 X，用户当面说 Y，按 Y 执行"）。
- 标 `[用户未直接沟通]` 时，遇到与用户既有偏好明显冲突的内容，先停手回报，不自行扩大解释。
- 接收方不得自行改写标记；转述他会话指令时必须原样带上原标记，并说明来源会话。

## 6. 异常必须落台账

- 遇到任何异常（报错、卡死、识别恒不命中、坐标点不中、设备异常），**必须登记进 `docs/问题登记.md`**。
- **不许只在回报正文提一句**：回报里可以摘要，但台账里必须有条目（编号、现象、影响、证据、状态）。
- 登记要求与状态定义见 `问题登记.md`；证据必须是真实路径，查不到证据就写 `待复现` 并注明缺什么。
- 修复完成后回填状态 `已修复`，附提交 hash 与验证方式（校验 PASS / 实机复核）。

## 7. 模拟器排他

- **同一时刻只允许一个会话操作模拟器**，并发仍然禁止。
- **串跑口径**：**同一条链上可以连续跑，不必每个任务前重新确认设备空闲**（例如同一任务的
  多轮循环、同一链内的前置→主任务→收尾）。
- **只在切换任务 / 换会话接手时确认设备空闲**：确认无其他会话占用、无残留战斗页/任务进程，
  必要时向用户确认；确认通过后即可继续串跑。
- 实机操作的申请、时长与交还标准按 [`docs/device.md`](device.md)「真机使用协议」执行
  （单次上限 25 分钟；交还时回主界面、保持横屏、不 launch）。
- 未获准不得触碰设备；纯代码/文档任务默认不连设备。

## 8. 审批边界

**在用户已明确授权的范围内，中间产物不停、不等审批，直接产出并回报。** 不得自行加设确认关卡
（如"要不要我继续""等你确认再动手"），**自造审批关卡视为流程违规**，按 §6 登记进问题台账。

只有以下三类情形**必须停下来问**：

| 类别 | 具体情形 |
|---|---|
| 超出授权范围 | 操作别人项目的模拟器实例、删除任何数据、修改他人配置/环境 |
| 不可逆操作 | 删除文件/目录、覆盖备份、重装依赖或模拟器、`git reset --hard` 等 |
| 需要用户亲自到场 | 实名认证、账号登录形态确认、涉及用户账号/支付的操作 |

停下来问时，必须写清：要做什么、为什么超出边界、不做的后果、可选的替代方案。

### 8.1 壳进程可由自动化自行关闭（2026-11-06 用户长期授权）

- **`MFAAvalonia.exe`（壳）允许自动化自行关闭**，不需要每次单独申请。它是改实例配置、重载
  `interface.json` 的前置动作，属于已授权范围，**不算"不可逆操作"、不得据此自造审批关卡**。
- **关闭范围只限壳进程本身**：**不含游戏进程**（`com.megagame.crosscore.bilibili`），
  **也不含模拟器**（`MuMuPlayer` / `MuMuManager` / 实例进程）。游戏与模拟器一律不碰；
  退出游戏仍走任务内既有节点，不得用 `Stop-Process` 顶替。
- **关壳前必须确认没有正在跑的任务**：壳日志无进行中的 `ExecuteTaskQueue`、无 `MaaFW`
  子进程在操作设备、没有任务链正在跑。有任务在跑就等它结束（或按用户指示 `StopTask`），不得硬关。
- 关壳后按 §7 确认设备空闲再接管；关闭口径仅 `Stop-Process -Name MFAAvalonia`，不做其它动作。
- **为什么必须关**：壳退出时会把**内存里的任务队列回写到 `config/instances/default.json`**，
  开着壳改配置必被覆盖（2026-11-06 14:31:12 实测，见 [`docs/问题登记.md`](问题登记.md) P-046）。
  正确顺序固定为：**关壳 → 改配置 → 复核 → 再开壳**。

## 9. 文档权威级别（单一权威）

- **唯一索引**：[`docs/README.md`](README.md)。每份文档一行，写明路径、职责、权威级别。
- **级别只有三档**：`权威结论` / `过程记录` / `已废弃`；**每份文档开头第一行必须标出级别**。
- **同一结论只允许一份 `权威结论`**；其余文档只能引用，不能复述结论正文。
- `specs/` 目录下**一律标 `过程记录`**，且开头必须指向对应的权威文档（如 `docs/coords.md`、`docs/device.md`）。
- 交付、汇报、代码注释引用结论时，**必须指向权威文档**，不许指向过程记录。
- 新增/更名/废弃文档时，同一次提交内更新 `docs/README.md` 与文档首行标记；发现多份文档复述同一结论，登记问题台账并按"单一权威"收敛。

## 10. 提交即推

- **每个功能点/修复完成并及时提交后，允许直接推送**，不再"攒够多批再统一推"。
- 推送前必须：`git fetch` → 确认当前分支与上游**无分叉**（`git log --oneline HEAD..origin/<分支>` 与
  `origin/<分支>..HEAD` 两侧都为空或只差本地新提交）→ 再 `git push`。
- 推送失败**不重试式死磕**：同一条推送最多试 2 次，仍失败就把状态报清楚（远端拒绝原因、是否分叉、本地待推提交）。
- **禁止 `force push`**，包括 `--force`、`--force-with-lease`；需要改写历史时先停手问用户。
- 例外：用户或统筹明确要求"本次不推"时，遵守该要求并在回报中注明"已提交未推送"。

## 11. 实例身份：认包不认端口

- 判定是否为项目目标实例，唯一标准是 `pm list packages` 输出中存在
  **`com.megagame.crosscore.bilibili`**（或 crosscore 系渠道包）。
- **端口只是参考值，不作为身份依据**（`127.0.0.1:16416` 之类可能被复用或重新分配）。
- 命中 **0 个**：报错停手，检查是否装错渠道包/实例未启动。
- 命中 **多个**：报错并交人工确认，**不许自选**一个继续执行。
- 设备操作与交还标准仍按 [`docs/device.md`](device.md)。

## 12. 判定与证据：卡住必看两帧

**多看截屏，卡住可以多看两次。** 任何"卡住 / 失败 / 无响应 / 被拦截"的判断，必须先对**同一画面连续截取至少 2 帧**，
间隔 **3–5 秒**，并比对两帧是否一致。

| 两帧比对结果 | 判读 | 允许的动作 |
|---|---|---|
| 两帧不同 | 仍在加载或动画播放中 | 继续等待，**不得判失败** |
| 两帧完全一致，且画面是弹窗 | 属于"等待人工操作" | 不是故障；按弹窗处理或等人工 |
| 两帧完全一致，且画面空白/异常 | 才可判为异常 | 记录证据后停手回报 / 登记问题 |

- **判断结论必须附上两帧的文件路径**；只有一张截图的结论视为**未验证**，不得据此停手、回滚或登记"已复现"。
- 该条同样适用于问题登记：登记"卡住 / 无响应"类条目时，**证据列至少写两个帧路径**（第二帧可用 `（第二帧）` 后缀区分）。
- 与既有条款的衔接：本条属于**§12（判定与证据）**的要求，和「坐标与识别素材必须来自实机原始帧」是同一类原则——
  **没有足够证据不下结论**（坐标条款见 [`docs/coords.md`](coords.md) 与 [`docs/项目规范.md`](项目规范.md) §9）。

## 13. 自检清单（提交或回报前快速过一遍）

- [ ] 回报第一行有状态头，且 `进度 / 用户已直接沟通 / 状态` 三项都填了。
- [ ] 本次是否有单步超过 3 分钟？有则已在回报里说明卡点。
- [ ] 是否有同类操作第 3 次尝试？有则已说明改了什么并已登记。
- [ ] 若结论是"卡住 / 失败 / 无响应 / 被拦截"，是否已连续截 2 帧（间隔 3–5 秒）并附上两个帧路径？
- [ ] 本次出现的异常是否已进 `问题登记.md`（不是只在正文提）。
- [ ] 指令标记是否原样保留、是否处理了"用户原话优先"的分歧。
- [ ] 是否确认没有其他会话正在使用模拟器，且以**包名**而非端口确认了实例身份（0/多命中已停手）。
- [ ] 是否自造了审批关卡？授权范围内的中间产物应直接产出，不得等确认。
- [ ] 新增/更名/废弃文档是否已更新 `docs/README.md` 与首行权威级别。
- [ ] 若执行推送：是否已 `git fetch` 并确认无分叉、未使用 force push；失败是否已如实回报。
