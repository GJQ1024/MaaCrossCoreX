## 2. 方案对库存的依赖条件

默认方案能跑通，必须同时满足：

1. 芯片仓库里至少有 **1 张 R2 档**且满足筛选面板 `芯片 = 神威` 的芯片（二者同时成立后列表非空）；
2. 该芯片**未装备、未锁定**，能出现在「芯片制作 → 新增 → 筛选」后的可制作列表；
3. 改造槽有空位（2026-11-04 实机为 `1/4`：1 个改造中 `03:59:06`、3 空；该占用由本次库存扫描误操作触发，见 §4）；
4. 燃料足够支付制作费用（费用闸 `芯片_费用闸` 只拦付费货币，不拦燃料）。

任一不满足时，筛选结果为「暂无芯片」，任务**先收尾回主界面、再判失败**，
不会继续滑动/空点到超时，也不会被上报成成功。

### 4.2 「库存不足」的失败语义：为什么之前是假成功，现在怎么修

**框架机制**（`repos/MaaFramework/source/MaaFramework/Task/PipelineTask.cpp`）：`PipelineTask::run()`
末尾 `return !error_handling`；节点动作失败会置 `error_handling=true` 并改走 `on_error`，
但**任何一次识别成功**（run 循环里的 `if (node_detail.reco_id != MaaInvalidId)`）都会把
`error_handling=false`。所以「失败后沿 `next`/`on_error` 走回主界面」的收尾链，一到第一个
识别成功的节点就把失败标记清掉，任务最终被判成功——这就是 `job.succeeded=True` 的来源。
**判失败与干净收尾不冲突，冲突出在「收尾链在同一 Pipeline 内」这个写法上。**

**当前做法**：`暂无芯片` 的 `task_fail` 增加 `cleanup_entry`——先在动作内部同步
`context.run_task("任务结束")` 完成回主界面收尾，**再返回 False**；节点的 `next` 与 `on_error`
都置空，外层的 `error_handling` 保持到循环结束，`job.succeeded=False`。失败原因由
`log.error` 输出：`任务明确失败：库存不足：默认方案 R2+神威 筛选后「暂无芯片」`。

**限制**：收尾发生在失败返回之前；若收尾自身抛出异常，`task_fail` 会记
`失败收尾「任务结束」执行异常`，仍返回 False（任务判失败，但设备可能停在原页）。

**替代方案**（某集成不支持动作内 `run_task` 时）：`暂无芯片` 的 `on_error` 置空直接判失败，
由调用方在 job 失败后单独 `post_task("任务结束")` 做收尾；代价是失败与收尾分属两个 job。

**验证状态**：**实机验证通过**（`chip_retry2`）：`job.succeeded=False`，收尾链已跑、结束帧回主界面，
燃料/星币/粲晶/改造槽均无新增消耗。离线侧另有 `py_compile`、`validate_resource` PASS、框架源码核对。
上表 48.9s 那轮（`chip_retry1`）仍是修复前的假成功记录。
