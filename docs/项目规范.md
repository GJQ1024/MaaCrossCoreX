## 2. 命名规则

### 2.1 pipeline 文件名
- 用**中文任务名**，`.json` 后缀，如 `每日探索.json`、`周本.json`、`通用-扫荡.json`。
- 通用/共享流程加 `通用-` 前缀；渠道专属放 `pipeline/<渠道>/` 子目录（如 `bilibili/pipeline/`）。
- 流程示意文件命名 `<任务>-现行Pipeline流程示意.json`，放 `docs/mpe/`，**不进 `pipeline/`**。

### 2.2 节点名
- **中文命名 + 前缀约定**：`<任务名>_<步骤语义>`，如 `每日探索_入口`、`主线刷取_区域列表上滑`。
- 子流程入口节点用 `<任务名>_任务` 或直接 `<任务名>`（需与 `interface.json` 的 `entry` 一致）。
- MPE 外部子任务节点用 `$__mpe_external_<节点名>_<任务名>`，配置节点用 `$__mpe_config_<任务名>`。
- 锚点设置节点名与锚点名一致，如设置 `"anchor": "主界面"` 的节点可命名 `通用_确认主界面`。

### 2.3 锚点名 `[Anchor]`
- 锚点名用**界面语义**，如 `主界面`、`芯片卡片`；引用写成 `"[Anchor]主界面"`。
- 引用锚点的节点必须保证上游已设置该锚点，否则动作失败（见 `coords.md` §3）。

### 2.4 agent 自定义动作名
- 文件名：`<域>_pipeline.py` / `<域>_domain.py` / `<域>_state.py`，如 `chip_pipeline.py`、`arena_pipeline.py`。
- 识别类函数：`def <域>_state(...)`，回传识别框；无框回 `None`（**禁止回 `(0,0,0,0)`**，与 `arena_pipeline` 一致）。
- 在 `agent/main.py` 的 `register_recognizer` / 动作注册表中显式注册，未注册的识别恒不命中。

### 2.5 测试脚本命名
- 离线单测：`tools/test_*.py`（pytest 风格，可无网络无设备运行）。
- 离线验证：`tools/verify_*.py`（带断言的资源校验）。
- 实机一次性脚本：`sandbox/run_*_once.py` / `sandbox/probe_*.py`，**不入库**。

## 4. interface.json 规范

`assets/interface.json` 是任务对外的唯一入口定义。

### 4.1 task
每个任务必须含：
- `name`：任务名（中文，与 pipeline 入口对应）。
- `entry`：入口节点名，必须存在于某个 pipeline 文件中。
- `doc`：一句话说明（无则写 `"无"`）。
- `option`（可选）：引用 `option` 字典里的选项名列表。
- `pipeline_override`（可选）：覆盖指定节点的字段（如角斗场覆写 `首页_出击.next`）。

### 4.2 option
- `option` 是**顶层字典**，key 为选项名（如 `芯片制造_等级`），value 含 `type`/`label`/`default_case`/`cases`。
- 每个 `case` 可含 `pipeline_override`，覆盖节点字段（如 `expected`）。
- 选项命名：`<任务名>_<语义>`，跨任务复用的通用选项不加任务前缀（如 `游戏渠道`、`MuMu实例`）。

### 4.3 pretask
- `pretask` 是数组，每项含 `name`/`label`/`description`/`exec`/`args`。
- `exec` 用相对路径 `../../python/python.exe`（指向打包后的 Python），`args` 指向 `agent/` 或 `scripts/` 下脚本。
- pretask 失败（非零退出）必须中止任务，不得静默忽略。

### 4.4 新增任务的硬性要求
1. 有**入口节点**（`entry` 指向的节点存在）。
2. 有**成功出口锚点或结束节点**：任务完成后回到主界面或停在明确页面，不得悬空。
3. 有**超时**：每个节点设 `timeout`，长任务的关键等待节点不超过 30s。
4. `interface.json` 的 `task.entry` 与 `option` 引用通过 `tools/validate_resource.py` 校验。

### 4.5 任务分组
- 顶层 `group` 与任务级 `"group": ["组名"]` 是官方 schema 字段；一个任务只取 `group[0]`，同组成员在 `task` 数组里尽量相邻。
- **当前壳（MFAAvalonia v0.1.3）不渲染任务列表折叠**：`group` 只影响「+ 添加任务」对话框；左侧队列是扁平列表（`install/libs/MFAAvalonia.Core.dll` 中只有 `BuildGroups`，无 `IsHiddenByGroup` / `HasGroupHeader` / `RefreshTaskGroups` 等符号）。
- 因此需要“视觉分组”时，**用任务名前缀**（如 `商店购买_每日免费礼包`），并同时预置 `group`；`name` 只是显示名，改名不影响 `entry`、`next`、`[JumpBack]`、`pipeline_override`、`task_memory` 参数与 `purchase_whitelist.json` 的 `store_key`。
- 改名后需同步 `install/config/instances/*.json`：`CurrentTasks` 与 `TaskItems[].name` 的 key 是 `任务名<|||>入口`，旧名不同步会导致已保存的队列顺序/勾选失效。

## 5. 提交规范

- **一个目的一个提交**：pipeline 坐标迁移、bug 修复、文档更新分别提交，不混在一起。
- **提交信息格式**（conventional commits）：
  - `feat:` 新功能 / 新任务接入
  - `fix:` bug 修复
  - `refactor:` 重构（不改行为，如坐标相对化）
  - `docs:` 文档新增/更新
  - `test:` 测试新增/更新
  - 示例：`refactor(coords): 芯片清理改为点识别框中心`
- **提交前必查**：`git log --oneline -3`，确认最近三条是自己的改动，防止夹带别会话的未提交改动；`git status --short` 确认只暂存了本次目的的文件。
- **不 push**：推送由统筹决定，本地提交即可。
- **分支策略**：日常工作在 `feat/relative-coords` 上进行；不在该分支上直接 rebase 他人提交；合并上游 MCCA 改动走单独 `merge` 提交。

## 6. 验证规范

- **改 pipeline 必跑校验**：在主仓库根目录执行 `tools/validate_resource.py`，退出码 0 才算过。
  - 完整命令（需带 `maa` 包的 Python，如 `MAA/sandbox/venv`）：
    `<带 maa 的 python> tools/validate_resource.py --resource assets/resource`
  - 校验项：Resource 加载、节点引用、模板图存在、锚点设置、绝对坐标硬检查（`MIGRATED_FILES` 内）、interface.json task entry 存在。
  - 依赖：`maa` 包（MaaFramework Python 绑定）；原生库路径由脚本自动向上搜索 `sandbox/MaaFramework-*/bin`，也可用环境变量 `MAAFW_BINARY_PATH` 覆盖。
- **agent 改动要有离线单测或 `verify_*.py`**：新识别函数需写 `test_*.py` 覆盖有框/无框/多框场景，实机不可用时用合成帧或离线截图。
- **实机验证必须留证据**：桌面截图（非 adb 截图）+ 关键数据（如非黑区域 bbox、耗时、退出码）；截图放 `sandbox/`，结论写 `docs/`。
- **改 `pretask_landscape.py` 或设备相关脚本后**：必须实跑一次受影响任务，确认横屏切换与帧预检正常。

## 8. 设备使用协议

> 详见 [`docs/device.md`](device.md)「真机使用协议」一节。本节为摘要。

- **同一时刻只有一个会话操作模拟器**；实机操作前必须向用户申请，说明内容、预计时长、消耗资源、预期结束状态。
- **禁止** `cmd window user-rotation` / `cmd window user-rotation lock`（会把 guest 搞崩）。
- **禁止**随意 `settings put system user_rotation`（游戏 Activity 方向锁压过 settings，无效）。
- **`wm size` 只在显示修正前置里用**：`scripts/pretask_landscape.py` 的 `ensure_landscape_orientation()` 执行「竖→横→reset」三步切换；其他脚本不得自行调用 `wm size`。
- **禁止** `svc wifi disable` / `svc data disable` 做断网注入（会弄宕 Android 子系统）。
- **单次占用上限 25 分钟**；交还标准：回主界面、保持横屏、不 launch、记录耗时与结束状态。

### 8.1 待机画面两类：游戏屏保 vs Android 系统锁屏（2026-11-06 用户澄清）

| 判据 | 游戏屏保（game_screensaver） | Android 系统锁屏（system_lock） |
|---|---|---|
| 前台 `mCurrentFocus` | `com.megagame.crosscore.bilibili`（游戏 Activity 仍在前台） | `com.android.systemui` / Keyguard |
| `isKeyguardShowing` | false | true（MuMu 可能报 false，须同时看前台包名） |
| 外观 | 游戏 CG 全屏 + 左下大号时钟/日期/电量 + 右下圆形刷新图标；无系统状态栏 | 系统壁纸 + 居中时钟/日期；有状态栏/通知/上滑提示 |
| `svc power stayon true` | **无效**（游戏客户端自己计时触发） | 有效（阻止系统熄屏） |
| 唤醒方式 | 轻点中性点 `(1200,400)` 或按一次 BACK，**下一帧复核** | `KEYCODE_WAKEUP(224)` + `swipe 640 620 640 160 300` |
| 置信度 | 前台=游戏 + keyguard=false + 三要素 → 高 | keyguard=true 或前台=SystemUI → 高；前台读不到只能记 low |

- **视觉三要素（时钟+日期+电量）不是锁屏判据**：它只说明「这是待机画面」，两类都会出现。旧实现据此直接判系统锁屏，故把游戏屏保误判成锁屏（P-051）。
- **中性点 `(1200,400)`**（1280×720 右缘中段空白）：避开新途补给/星贸凭证/活动（y<180）、满赠馈赠（x≤1010）、出击（x≤1015 且 y≥470）、底部功能栏（x≤1105）、左侧菜单（x≤270），以及屏保右下圆形刷新图标（≈965,657）。2026-11-06 实测在主界面点击该点无任何跳转。
- **复核才算唤醒**：下一帧重新截图 + 重新诊断，前台离开待机画面才记「复核通过」；若停在公告/弹窗，按 §20.2 既有策略处理。连续 6 帧未离开 → `screen_stuck` 失败，禁止盲重跑。
- **代码唯一入口**：`scripts/device_judge.py::diagnose_screen()`（判据）与 `tap_neutral()/press_back()/unlock_system()`（动作）；调用方 `scripts/account_switch.py`。pipeline 侧 `启动_唤醒待机页面` 只处理屏保：OCR 命中时钟后点**识别框中心**（时钟是纯显示区，属无副作用空白点击，且遵守 `docs/coords.md` §4 不写绝对 `target`），不做上滑。
- **证据帧**（均判为游戏屏保）：`sandbox/tutorial_run3/frames/s00_lobby_before.png`（12:15 / 2026/11/03 / 84%）、`sandbox/tutorial_neg/33_wake/001.png`（11:25 / 90%）、`sandbox/mail_state2.png`（05:01 / 71%）；`sandbox/screen_after_tap.png` 为轻点后回到补给站主界面。
- **`svc power stayon` 现状**：对游戏屏保无效，但能阻止真正的系统熄屏（实测 `screen_off_timeout=1800000`），故**保留**。设置台账见 `docs/device-change-log.md`「2026-11-06 电源设置」。

## 9. 坐标与识别素材必须来自实机原始帧（硬条款）

**坐标与识别素材必须来自实机原始帧**：roi / target / target_offset / 模板图，一律从 adb 原始分辨率
（1280×720）截图量取或裁取，并在提交信息或节点注释里标出来源截图；任何"按比例换算""凭经验推算"
的值一律不得作为最终值，只能标 `TODO(待实机校准)`，且不得进入主线。

- 量取方式：在原始帧上按像素边界（颜色/边缘）量出 bbox，或直接用模板匹配得到 bbox；不得先在
  缩放后的预览图（例如 1024×576）上读数再换算。
- 截图证据留在 `shots/<主题>/`（不入库），节点注释/提交信息里写清用的是哪张原始帧。

## 11. 跨会话协作

三份必读文档（不在此重复正文）：

| 文档 | 作用 |
|---|---|
| [`docs/README.md`](README.md) | 文档唯一索引与权威级别登记（`权威结论` / `过程记录` / `已废弃`） |
| [`docs/问题登记.md`](问题登记.md) | 跨会话共享问题池；开工前必读，异常当场登记，同一问题只补证据、不新建条目 |
| [`docs/跨会话协作规范.md`](跨会话协作规范.md) | 分段执行、卡住即停、固定状态头、指令标记、异常落台账、模拟器排他、审批边界、文档权威、提交即推、实例认包 |

**必读要求**：

1. 任何会话**开工前**先读 `问题登记.md`，确认本次任务是否涉及已登记问题或"登记为例外"的节点。
2. 每次回报**第一行**写固定状态头：`进度: 第 n 步 / 共 m 步 | 用户已直接沟通: 是/否 | 状态: 进行中/卡住/完成`。
3. 长任务必须切段、每段结束即回报；单步约 3 分钟无结果，或同类操作连试 2 次无效，必须停手回报。
4. 指令必须带 `[用户未直接沟通]` / `[用户已直接沟通]` 标记；标"已直接沟通"时，用户当面说法优先，冲突需在回报中说明分歧。
5. 异常必须登记进 `问题登记.md`，不得只在回报正文提一句。
6. 模拟器同一时刻只允许一个会话操作，接手前先确认无人占用；实例身份**认包不认端口**（`pm list packages` 命中 `com.megagame.crosscore.bilibili` 及 crosscore 系渠道包，0 个报错、多个交人工）。

## 12. UI 开关状态不得假定继承（通用硬条款）

**任何会被用户手动改变、且会「粘住」上一次设置的 UI 开关，自动化都不得假定其状态，必须在执行前主动纠正。**

- 典型对象：战斗「自动战斗」、连战/循环、快进、技能演出跳过、自动补给等。
- 错误写法：`expected: "on"` 一次性校验，判不到就中止——用户上次手动关掉后必空跑。
- 正确写法（三段式）：
  1. **已是目标态** → 直接通过，不点击；
  2. **明确是相反态** → 点击纠正 → 等待 → **重新识别复核**；复核仍是相反态再点一次（限次防连点），仍不成才失败；
  3. **识别不到（过场/未加载）** → 不是失败，继续等待；预算 ≥60s，控件出现即回到 1/2。
  只有总预算耗尽仍既判不到目标态、也无法点击时才失败。
- 竞技场落地样本：`agent/combat_autobattle.py` + `assets/resource/pipeline/base/模拟军演.json::竞技场_确认自动战斗`。
- 相关台账：`docs/问题登记.md` P-017。

## 13. 「无响应兜底」先分类再选手段；重启是兜底，不是首选

**同为「卡住不动」，判据不同则手段不同，禁止一套兜底通吃。手段按代价从轻到重分层：
业务层撤退/刷新优先，重启游戏进程是最后一层兜底。**

手段优先级（从轻到重）：

1. **业务层撤退/返回**：暂停 → 退出战斗 → 回列表 → 刷新 → 重挑；能点、能退时优先；
2. **刷新/重挑**：仍不重启进程，保留登录态与进度；
3. **`am force-stop` + `monkey` 重启游戏进程**：只在下面两种情形允许——
   - **画面完全不变**（P-010：连抓 5 帧，唯一 hash < 2）；
   - **竞技场 60s 超回合，撤退链走完仍退不出去**（暂停菜单/确认弹窗点不掉，或确认后 40s 未回列表）；
4. **重启模拟器/实例**：不在自动化内，交人工。

除上述两种情形外，**「画面在变但没进展」一律不许重启游戏进程**，必须走业务层撤退/刷新。

| 类型 | 判据 | 正确手段 | 禁止 |
| --- | --- | --- | --- |
| **画面冻结**（P-010） | 连抓 5 帧，唯一 hash <2（画面完全不变） | `am force-stop` + `monkey` 重启进程并回大厅 | 用业务层撤退/返回：冻结时点击也不响应 |
| **业务超时**（P-018） | 画面仍在变（HUD/回合推进），但 60s 不出结算 | **先** 暂停→退出→回列表→刷新→重挑；**撤退链走完仍退不出去才** `am force-stop` + `monkey` 重启进程 | 画面仍在变、撤退链还没走完就重启（白丢登录态与进度） |

落地判据要求：冻结用「**帧 hash 是否变化**」，超时用「**agent 侧墙钟**」（Pipeline 节点之间
无法累计墙钟，`timeout`/`post_delay` 拼不出「从 HUD 出现起 60s」的语义）。
相关台账：`docs/问题登记.md` P-010、P-018；竞技场细则见 `docs/arena.md` §5。

## 14. 识别方式选型：先选判据，再谈阈值

**一句话规则：有明确图案用模板匹配，有文字用 OCR，只剩纯色或图案本身易变才用颜色；颜色必须配形状约束，判据冲突时宁可不点。**

| 目标特征 | 首选判据 | 可执行要求 | 反例 / 禁用 |
| --- | --- | --- | --- |
| 有稳定图案的按钮、图标、入口 | `TemplateMatch` | ROI 贴紧目标；阈值必须在**实机原始 1280×720 帧**上实测，余量 ≥0.05 | 阈值 0.8 而实测 0.802（余量 0.002）——看起来能过，实际一帧抖动就掉；类间距本身 <0.10 的模板（Finger 正例 0.7582 / 负例 0.7257，只差 0.0325）无论怎么调阈值都给不出两端 0.05 余量，必须重裁模板（P-023） |
| 文字、弹窗、次数、余额、体力 | `OCR` | 两种用途分开写：**读内容**（次数/余额/体力，需校验数值合理性）；**找点击点**（点 OCR 框中心，点击后必须重新截图判定，不能按固定延时盲点） | 用颜色判「次数/余额」：数字字体与背景随时变化，颜色计数不稳定 |
| 纯色块，或图案易变（变形/碎裂/被特效覆盖） | `ColorMatch` + 形状约束 | 原生 `ColorMatch` 只能设 `count` **下限**；要「封顶」或区分真目标/撞色，必须改用自定义识别补面积/宽高比/填充率/多块并集外框 | 只写 `count: 1`（原生语义是「≥1 像素」）；教程金框 `count: 250` 挡不住演出帧 1996–4168 的金色特效（P-021）；金色横幅撞色 774 像素落在计数区间内（P-019） |
| 判据相互冲突、样本不足 | **判不出** | 取向固定为**假阴性优先**：宁可多等几帧判失败，也不点不确定的目标 | 误点付费按钮、误退战斗的代价远高于「多等几帧后判失败」；禁止用弱判据兜底强判据 |

**原生 `ColorMatch` 的能力边界（选型前必须知道）：**

- `count` 是**下限**，而且**只有一个方向**。MaaFramework 的过滤条件是 `res.count >= count`
  （`repos/MaaFramework/source/MaaFramework/Vision/ColorMatcher.cpp::add_results()`），
  参数类型是 `int`（`Vision/VisionTypes.h` `ColorMatcherParam::count`）。
  只写单值 = 只有下限，等于「≥N 像素即命中」。
- **原生无法封顶**：写成 `count: [min, max]` 会被 PipelineParser 以 `type error [key=count]` 拒绝，
  整个 pipeline 加载失败（2026-11-04 `tools/validate_resource.py` 实测）。需要上限时只能：
  ① 换 `TemplateMatch` / `OCR`；② 写自定义识别（推荐）；③ 缩 ROI 到只含目标，让「≥N」天然接近等价。
  禁止把 `[min, max]` 留在 JSON 里——它不会更严，只会让资源加载失败。
- `connected=false`（默认）：全部匹配像素**联合成一个结果**，框是联合外接矩形，中心由所有命中像素决定。
- `connected=true`：每个连通块单独成结果，再按 count 做 NMS 取主块。细边框/镂空图案会被切碎，
  「最大连通块」的中心会乱落——定位点击点时必须用 `connected=false` 的联合框，或改用模板匹配。
- 宽高比、填充率、多块并集外框等**形状判据 pipeline JSON 无法表达**，必须落到自定义识别
  （样本：`agent/combat_autobattle.py::_amber_metrics`）。

**禁止「假安全」辅助条件：** 若某条辅助判据在真实帧上永远不触发（例如阈值 0.8 配实测 0.802 的模板、
或 count 下限大于 ROI 面积的计数），它不是更严，而是不生效；应删除或改判据，不得留在配置里制造安全感。

相关台账：P-002（颜色 bbox 被光晕抬高）、P-019（颜色计数被金色横幅撞色）、P-020（原生 `ColorMatch` 无法封顶）、P-021（教程金框被金色特效撞色）、P-022（颜色判据恒真/缺 ROI）、P-023（模板类间距不足）；本条是选型规则，不新增问题条目。

## 15. 按钮可用性必须纳入判据（不能只看「同模板命中」）

**可点击按钮的识别必须同时覆盖「可用态」和「禁用态」；只要两种状态共用同一个模板，模板分数
就不能作为可点依据，必须再叠加状态判据（颜色/饱和度、状态文字「已领取/已完成」、置灰标记）。**

可执行判断：

1. 找到按钮的模板后，先在**同一功能的可用态帧与禁用态帧**上各跑一次模板分数；
2. 若禁用态分数也 ≥ 阈值（说明模板分不开两态），**禁止抬高阈值了事**，必须加状态判据：
   `And(TemplateMatch + ColorMatch)` 或 OCR 状态文字；
3. 颜色判据必须在两帧上给出计数：禁用态计数 < `count` 下限，可用态计数 ≥ `count` 下限；
   模板阈值保留实测两端余量 ≥0.05；
4. 验证必须贴出「可用态通过、禁用态被挡」的两帧结果，只验正例不合格。

**反例（2026-11-04 实机发生，非理论风险）**：`领取奖励.json::每日任务_一键领取` 原本只有
`TemplateMatch 一键领取.png`，灰态与可用态同模板，实机分数 0.826 / 0.802（阈值 0.7），
两次都命中并点击，点完没有「获得物品」，属空点灰按钮。修复后改为
`And(TemplateMatch threshold 0.7 + ColorMatch count 800)`：可用态模板 0.9985 / 金色像素 3309，
灰态模板 0.826 / 金色像素 0，灰态由颜色判据挡掉。

## 16. `expected` 只写通用词且无 ROI 属高危写法

**OCR `expected` 不得只写「基地」「任务」「领取」这类通用词且不带 `roi`；必须二选一：
加紧贴目标的 `roi`，或改用独占模板/独占词。通用词命中的是「页面里任意一处包含该词的文字」，
不是目标按钮。**

可执行判断：

1. 上线前对 `expected` 的每个词做一次「全屏反查」：该词是否也出现在正文、说明、tooltip、
   其他按钮里？只要存在，就不是独占词；
2. 无 `roi` 或 `roi` 覆盖面积 > 目标按钮面积 3 倍时，禁止只用通用词；
3. 优先用目标按钮的独占模板（图标/整颗按钮），OCR 只用于「读内容」而不是「找点击点」；
4. 验证必须给出「目标页命中」与「含该词的正文页不命中」两帧结果，并贴分数/命中框。

**反例（2026-11-04 实机发生）**：`芯片制造.json::进入基建` 原为 `expected:["基地"]` 且无 ROI，
命中了正文 tooltip「原料可用于升级基地和交易，升」，导致点歪进入基地建造列表（`seq_chip02.png`）。
修复后改为底部按钮图标模板 `基地.png`（46×46）+ `roi [560,600,150,120]` + `threshold 0.7`：
主界面正例 0.846–0.883（最低余量 0.146），基地建造页负例 ≤0.325，正文 tooltip 完全不在 ROI 内。
注：该按钮的 OCR 在 1280×720 帧上读不出文字（实测 0 条），不能靠 `expected` 兜底，必须用模板。

## 17. 「扫一批/轮一遍」的循环，每一步动作前必须先确认所在页面

**任何按固定坐标批量点击的循环（扫库存、翻列表、逐档筛选、轮奖励行），每一次动作前都必须
先对「当前目标页」做一次确认识别（页标题/页标志模板/筛选面板特征）；确认不到目标页就立即
停手并记录，禁止沿用上一页的坐标继续点。**

可执行判断：

1. 循环体第一句是「页面确认」，不是「点击」：确认命中目标页标志才执行该页坐标；
2. 每完成一次会改变页面的动作（返回、确定、选择卡片）后，重新确认当前页；
3. 一旦确认失败或命中了另一页的标志（例如回到了改造中心、进了详情页），立即 `break`，
   把当前帧和已完成的步数写进日志，交给人判断，不得「按原计划再点几下试试」；
4. 只读操作也要遵守：打开卡片详情会改变页面，后续必须重新定位，不能复用网格坐标。

**反例（2026-11-04 实机发生，造成真实消耗）**：库存扫描第一版在「选卡后已退回改造中心」，
仍继续按芯片网格的坐标点击，误载入一张芯片并启动了改造——`可改造 1/4`、首槽
「改造中 03:59:06」（证据 `sandbox/shots/_scan_grid2.png`；同批 `_scan_a4.png` 为误操作前
`可改造 0/4`）。根因不是坐标算错，而是**没有先确认「已经回到目标页」就按旧坐标动作**。
修正后的扫描循环只允许在网格页点「品质/类型/重置/确定」，且每次动作前先确认筛选面板存在。

## 18. 付费闸必须 fail-closed：判不出即不买

**任何会花货币或可能扣费的动作之前，必须先拿到「阳性放行」判据（明确识别到「免费」或
「余额充足」）；否定判据（价格符号、扣费文案）未命中不等于免费，只能当作「无法确认」，
必须中止并判失败。**

可执行判断：

1. 「价格/扣费判据命中」与「判据未命中」是两条不同分支：命中 → 退出，不得购买；
   未命中 → 不允许直接执行购买，必须再走一次阳性确认（免费文案 / 余额充足状态）；
2. 阳性确认也判不出时，用 `task_fail`（`cleanup_entry` 指向现有回主页收尾链）中止，
   节点 `next`/`on_error` 留空，避免收尾链识别成功把 `error_handling` 清零；
3. 禁止把「识别失败」直接接到购买/扣费节点（旧写法 `on_error → 购买` 等价于默认放行）；
4. 余额类闸要区分「余额低于下限（正常结束）」「余额充足（放行）」「读不到（失败）」三态，
   不得把后两者合并到同一个出口。

**反例（2026-11-04 静态排查确认）**：

- `每日免费礼包.json::礼包_价格闸` 原 `on_error → 礼包_购买`：价格 OCR 超时/读不到就直接买；
  且 `礼包_免费` 的 `next` 末尾挂着 DirectHit 的 `礼包_退出`，导致「无价格 → 购买」分支
  实际不可达、购买节点永不被执行。
- `限时贸易.json::限时贸易_余额判定` 原 `on_error → Buy_something`：把「余额充足」和
  「判不出来」混成同一个出口。现拆出 `coin_ok` 阳性判据 + `限时贸易_余额充足` 节点，
  判不出来改走 `task_fail`。

## 19. 证据先行：出问题先存图，数字必须配图

**任何异常、失败、卡点、判据不命中，第一动作是保存当时那一帧，再写文字报告；报告里任何
数字（燃料、进度、亮度、耗时）都必须给出对应截图路径，没有图就标「无证据」，不得混进主结论。**

### 19.1 每战四帧必存（硬条款）

每次进入战斗，以下四个时刻必须各存一帧到 `sandbox/shots/<MMDD>_主线首通/`：

| # | 时刻 | 必须包含的信息 | 用途 |
|---|---|---|---|
| 1 | 编队页（点「开始行动」前） | 右下「燃料-XX」+ 顶部「当前/上限」 | 唯一能直接测出单场成本的读数 |
| 2 | 点「开始行动」后一瞬间 | 战斗进场/HUD | 开战时间点，核算期间自然回复 |
| 3 | 结算页出现 | 胜利/失败、星级 | 战斗结果、结算时间点 |
| 4 | 回到主界面 | 顶部燃料 | 任务前后净变化对账 |

### 19.2 数字配图

- 燃料读数：日志写 `燃料 tag=值 @时间 图=路径`，数字与该帧同源（同一张图 OCR）；
- 进度/扫荡亮度：核验日志必须带该帧路径；
- 编队页「燃料-XX」：显示值与主界面净变化对不上时，写清差多少、卡在哪一步，不得用主界面差值冒充实测；
- 编队页没有「燃料-XX」字样时，明确记「该页无此读数」，**不得**用别处读数替代。

### 19.3 失败帧

失败/卡点路径（点不到、看不见、超时、页面不认识）一律先 `_fail_shot(context, stage)` 落盘，
再在报告里给出路径；告警级别为 `error`，不得只有一句文字描述。

### 19.4 非白名单页面

兑换站点、奖励面板、公告等意外页面出现即存快照 + 一条告警，只记录不判据。

**落地**：`agent/mainstory_pipeline.py` 的 `_snapshot` / `_fail_shot` / `_fuel`；
相关台账见 `docs/问题登记.md` P-035。

### 20.4 购买白名单与付费闸（设计口径）

- 白名单结构（三级，落盘 `config/purchase_whitelist.json`）：
  `{"stores": {"<store_key>": {"name": "...", "enabled": true, "items": [{"name": "...", "enabled": false, "currency": "free|ingame|paid", "price": N|null, "max_price": N}]}}}`
- **同名不同价（2026-11-11 用户确认，方案 A）**：`wtrade_rare` / `gladiator_shop` / `mirror_shop` 的匹配键是「名字 + 价格」。货架同名商品出现多档价格时，白名单条目必须配 `price` 才买；未配 `price` 判歧义并跳过（fail-closed），不猜档位。同名只有一个价格时不强制比价（阶梯涨价属正常）。多价命中后按货架格位（页/行/列）锚定，重扫时跟住同一档，涨价不会串到另一档。`price` 只做档位区分，不参与金额拦截。
- **store_key 为固定枚举**：`gift_daily_free` / `limited_trade` / `wtrade_rare` / `wtrade_alien` / `gladiator_shop` / `mirror_shop`。**未列出的 store 一律整店关闭（fail-closed）**，不得按「看起来免费」临时放宽。
- 条目级默认 `enabled=false`，**须用户逐项勾选**后才可能购买；`max_price` 预填为实测当前售价，**只作参考价展示，不参与拦截**（2026-11-06 用户确认：三家店是阶梯式涨价，涨价属正常机制，勾了就要买）。
- **面板「物品选择」优先（2026-11-06 用户确认）**：`wtrade_rare` / `gladiator_shop` / `mirror_shop` 三条任务各有一个多选 option（`商店购买_罕见星尘区_物品选择` / `角斗场兑换_物品选择` / `镜像竞技兑换_物品选择`），case = 该店白名单商品名，**默认全不勾**。实例 `TaskItems.option.selected_cases` 非空 → 本次只买勾选的名字（可买 `enabled=false` 的条目）；为空或没有该选项 → 回退 `enabled=true`（旧行为）。**面板只决定「买哪些已登记商品」**：不能开付费、勾了白名单未登记的名字一律拒绝；价格不再作为拒绝理由。
- `limited_trade` / `wtrade_alien` 两条老链路**按面板选项工作、不读白名单**（`limited_trade.py` / `alien_shop_marker.py` 直读实例配置），保持现状，不迁到白名单。
- **三道硬闸（顺序不可变，任一不过即不点）**：
  1. **付费货币闸**：售价区 OCR 命中 `¥ / ￥ / 粲晶 / △ / 凭证 / 充值 / RMB` → 直接 `task_fail`（判不出也算不通过）；页级扫描只覆盖货架网格，导航/页签 chrome 用 `ignore_rois` 排除。
  2. **白名单闸**：商品名不在 `stores[store_key].items` → 不点；条目 `enabled=false` 且面板未勾选 → 不点；`currency=paid` → 不点。
  3. **余额保底闸（`balance_floor`，2026-11-06 取代价格闸）**：每店一个，白名单 store 级配置，**缺省 0（用户口径：勾了就买干净）**。买前 `余额 - 单价 < balance_floor` → 停止该店；`balance_floor=0` 时只有 `余额 < 单价` 才停，记「余额不足」并停止（不是跳过继续）。这是唯一的金额类拦截；`max_price` 只展示不拦截。
  候选按**白名单顺序**买（不按价格升序）：价格升序会让便宜条目吃光余额，用户排在前面的目标反而买不到。
  三道全过才允许点购买；动作成功后仍按 §18 fail-closed 复查（余额差值必须等于单价，对不上即失败停止）。
- **购买幂等（P-050）**：每次运行在 `sandbox/store_run/` 写 `<store>_<ts>.running`，结束改 `.done` 并写入成交量；5 分钟内发现同店 `.running`/`.done` → 记「疑似重跑，跳过」并成功退出，不重复购买。`dry_run` 不写标记。
- 购买弹窗本身可打开用于读取清单（不点「购买」），但一旦进入确认态必须可回退。
- **万物贸易所页签口径（用户截图核对，2026-11-05 修正）**：顶部页签需横滑，共 **8 个**，顺序固定为
  `罕见星尘区 → 传说星辰区 → 拓展研发所 → 自选星尘区 → 异星灰域 → 粲晶贸易区 → 装饰贸易区 → 微晶贸易区`。
  因此「**最后面三个**」＝ **粲晶贸易区 + 装饰贸易区 + 微晶贸易区**（此前「最后三个＝传说星辰/拓展研发/自选星尘」的说法作废）。前 5 个首屏可见，后 3 个需右滑露出。
- **不动区（用户决定，2026-11-05）**：传说星辰区、拓展研发所、自选星尘区、粲晶贸易区、装饰贸易区、微晶贸易区——**不接线、不采集物品表**，仅在文档留页签/货币判据。

## 23. 通用 UI 处理强制复用（2026-11-09 定稿）

**新任务遇到遮挡层、断线、返回、滚动、按钮判态、二次确认、资源不足时，一律复用下列通用节点，不许各写一份。**

| 场景 | 通用节点 | 实现/参数唯一来源 |
|---|---|---|
| 获得物品 / 战斗结算 / 公告 / 促销遮罩 | `通用-遮罩处理`（识别闸门 `ui_mask_probe` preset=any）→ `通用-遮罩_*` | `agent/ui_common.py::MASK_SPECS`、`MASK_ANY_ORDER` |
| 断线重连 / 被踢回登录页 | `通用-断线恢复`（OCR 闸门） | `MASK_SPECS.network_unstable/login_lost` |
| 返回口径 | `通用-返回`（`smart_back` 查表） | `ui_common.BACK_TABLE` |
| 滚动 / 翻页 / 回顶 | `通用-左滑一屏`、`通用-滚动回顶`（`ui_swipe`） | `ui_common.SWIPE_PRESETS` |
| 可点 / 灰态 | `ui_button_state` 自定义识别 | 通道差判据（brightness ≥ threshold） |
| 二次确认框 | `通用-二次确认_取消`（`ui_confirm_guard`+`ui_confirm_cancel`） | `ui_common.CONFIRM_WHITELIST` |
| 体力 / 次数不足 | `通用-资源足够` / `通用-资源不足_跳过` | `ui_common.RESOURCE_ROIS` |

三条硬规则：

1. **不许盲点**：每类遮罩/页面都要单独识别（OCR 或模板），命中才动作；禁止 DirectHit 分流器。
2. **`[JumpBack]` 目标不得是恒命中节点**：恒命中节点回跳后父节点重扫又命中自己，会无限重入（2026-11-09 16:25 实跑）。闸门必须是真实识别。
3. **关不掉要留帧并明确失败**：走 `ui_mask_snapshot` → `task_fail`，禁止静默卡住或吞掉失败。

例外：商店购买白名单保持专用，不并入通用二次确认。
